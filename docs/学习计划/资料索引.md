# 资料索引

## 使用原则

本索引以 2026-09-08、提交 `96617628e85227dedc05095717fbb1b7e878a975` 为基线。学习 pi 时，资料优先级是：

```text
当前源码、导出类型与可运行 examples
> 聚焦测试
> package README 与 docs
> CHANGELOG
> 较旧博客与第三方文章
```

原因不是“文档不可信”，而是仓库正在演进，当前已有少量文档示例滞后于导出 API。遇到矛盾时，必须通过类型、测试和最小运行实验确认，不能凭记忆选择一个版本。

## 三、文档漂移与版本核验

### 当前已知漂移

以下结论只针对本计划基线：

1. `packages/coding-agent/docs/sdk.md` 的完整示例仍从 `@earendil-works/pi-ai` 根入口导入旧 `getModel`；当前新代码应使用 `Models`/`createModels()` 与 Provider factories。弃用兼容 API 位于 `pi-ai/compat`。
2. 同一 SDK 文档的部分片段包含未定义的 `haiku`，以及已经滞后的 `Skill`/`PromptTemplate` 字段；当前类型要求使用 `sourceInfo` 等字段，而不是旧 `source`。
3. `packages/coding-agent/examples/sdk/README.md` 列出不存在的 `08-slash-commands.ts`；实际文件是 `08-prompt-templates.ts`。
4. examples README 的 Quick Reference 同样使用旧根入口 `getModel`，thinking level 列表也不完整。
5. 稳定 `AgentSession` 内部仍有 `pi-ai/compat` 使用，这是迁移中的内部实现，不是新 Agent 的 API 模板。
6. extension examples 的权限和 shell 示例是概念演示，不满足生产安全边界。
7. subagent example 是本地编排原型，缺少 wall-clock/token/cost 预算、durable recovery、严格输出校验和完整进程树治理。
8. Harness 文档明确标记 storage format 4 为 WIP；规范中的目标能力不等于当前全部实现。Work scheduling、Provider stream resume、multiple writable owners、replication 和 external-effect exactly-once 是明确非目标，不能再列成“等待实现”的 Harness 缺口。
9. `packages/coding-agent/test/agent-session-branching.test.ts` 与 `packages/coding-agent/test/agent-session-compaction.test.ts` 是 legacy real-LLM tests；检测到 Anthropic 凭据时会产生真实请求。默认学习命令使用 `packages/coding-agent/test/suite/` faux harness 与纯 SessionManager 测试替代。
10. `AgentSession` 与 `AgentHarness` 是两条运行线，但 Harness JSONL backend 已支持 legacy coding-agent v3 compatibility：只读 open 在内存归一，首次非空 format-4 commit 原子升级文件；这不同于尚未激活的 R11 schema migration。

## 四、术语表

| 术语 | 本计划中的含义 |
| --- | --- |
| Agent | 持有运行状态并驱动模型、工具、队列和事件的控制器，不只是一次 LLM 请求 |
| Agent loop | 根据 assistant/toolCall/toolResult/stopReason 推进的模型驱动循环 |
| Turn | 一次模型响应及其工具批处理边界 |
| Run | Agent 从输入开始到 `agent_end` 的进程内执行 |
| `agent_end` | 一次 agent-core run 的结束事件；AgentSession 仍可能进行自动重试或压缩后继续 |
| `agent_settled` | AgentSession 完成该 prompt 的所有 post-run 处理且回到 idle 后发出的高层终态 |
| Operation | Durable Harness 接受并持久推进的运行单元 |
| Lane | Harness 中限制同一并发域只能推进一个 operation 的逻辑执行通道 |
| Session | 多个消息、分支、配置与运行历史的逻辑容器 |
| Transcript | 已发生消息的事实记录；不等同于本次 Provider context |
| Context | 发送给模型的当前投影，可能经过分支选择、压缩和 Provider 转换 |
| Provider | 模型目录、认证和 API adapter 的统一边界 |
| Tool call | assistant 请求应用执行某工具的结构化内容 |
| Tool result | 应用执行后按 call ID 回传给模型的结构化观察 |
| Steering | 当前工具批完成后、下一次模型调用前注入的新指令 |
| Follow-up | Agent 本来将结束时，由外层循环开始处理的新输入 |
| Compaction | 用摘要加保留尾部构造更短 context；原始 session entries 仍保留 |
| Settlement | 一次 stream、tool、run 或 durable operation 到达唯一可观察终态 |
| Effect | 对外部系统产生的可能不可逆副作用 |
| Unknown outcome | 客户端不知道 effect 是否成功，不能按普通失败盲目重试 |
| Project Trust | 是否加载项目本地资源的信任决策，不是工具授权或 sandbox |
| Replay policy | Harness 在 effect pending 恢复时决定 safe replay 或 never replay 的声明 |
| Values/lists | Harness repository 中与 immutable entries 分开的事务性当前状态 |
| Tool step | 本计划预算中一次工具执行；不是当前 pi 的统一公共计量类型 |
| Faux provider | 产生确定性模型事件的测试 Provider；替代网络传输，不替代真实业务样本 |
| Admission | 接受任务或启动 turn/tool 前检查容量、权限和预算 |
| Fencing | 用单调令牌拒绝已失去所有权的旧 worker 写入 |
| DLQ | Dead Letter Queue，多次处理失败后等待人工或专门流程处置的队列 |
| Shadow | 复制真实输入做旁路运行，但结果不驱动正式业务副作用 |
| Canary | 只给小比例真实流量启用候选版本，以指标决定扩流或回滚 |
| RTO / RPO | 可接受的恢复时长目标 / 可接受的数据丢失时间窗口 |

## 五、应暂缓的资料

以下内容不是无价值，而是过早阅读的机会成本很高：

- `packages/coding-agent/src/modes/interactive/interactive-mode.ts`：完成 core loop 后再读。
- `packages/coding-agent/src/experimental/mini/` 与 `packages/coding-agent/src/experimental/services/`：理解稳定主线和 Harness 后再比较。
- plugin facets 与 mobile handoff 文档：作为架构演进研究，不作为当前稳定 API。
- multi-agent/subagent：单 Agent 的预算、取消、会话和副作用边界完成后再做。
- 任意 RAG 框架：先证明目标场景真的需要检索，并定义检索质量评测。

判断标准很简单：如果还不能解释一次 tool call 从 Schema 到 result 再到下一轮模型请求，就不应进入这些主题。

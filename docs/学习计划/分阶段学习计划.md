# 分阶段学习计划

## 计划约定

本计划默认 12 周、每周 8–10 小时。每周建议分配为：

- 30%：运行、打断点和记录事件。
- 30%：读类型、聚焦测试和实现。
- 30%：Python 复刻或故障注入实验。
- 10%：更新架构图、问题清单和结论。

每个阶段都以可验收产物结束。阅读页数、观看视频或“感觉理解了”不算通过。

12 周的可承诺终点是 **L1 内部只读原型 + 生产评审包**，不是已经承载真实生产流量的平台。课程内完成小规模真实脱敏评测、故障注入和上线演练；扩大到统计功效足够的评测集、真实 shadow/canary、写副作用、HA 与灾备属于毕业后的 L2–L4 迭代。只有实际证据达到[生产化能力清单](./生产化能力清单.md)对应等级的门禁，才能对外宣称该等级已经就绪。

本文严格区分两类实验：“网络隔离回归”使用 scripted/faux Provider、无凭据且无 egress；“非生产流量真实 Provider 评测”不接生产流量、不产生业务副作用，但仍会联网并消耗真实模型额度。后者不能简称为“离线测试”。

除非代码块内先切换目录，所有命令都假定从当前仓库根目录开始执行。测试命令使用 `git rev-parse --show-toplevel` 定位仓库根，避免上一条命令遗留的 cwd 影响下一阶段。

建议为学习记录固定以下模板：

```markdown
# 主题

## 我观察到的行为
## 源码证据
## 最小执行轨迹
## 不变量与失败边界
## Python 对应实现
## 尚未回答的问题
## 验收结果
```

### 动手实验

先列出当前已配置且获准用于学习的模型：

```bash
./pi-test.sh --offline --no-extensions --no-skills \
  --no-prompt-templates --no-context-files --list-models
```

只有模型、凭据来源、数据出境范围和 Provider 侧硬额度都已确认，才继续实验 A。若没有获准的真实 Provider，跳过实验 A，先运行[源码阅读与实验手册](./源码阅读与实验手册.md)第十四节的 `pi-ai` 与 `pi-agent-core` faux 聚焦命令，并从 `packages/agent/test/e2e.test.ts` 的 `handles a basic text prompt` 用例构造无工具 trace；把真实 SSE 观察记为待办，不能临时借用生产凭据。Provider 不支持硬额度时，必须先通过公司模型网关、一次性受限凭据或等价外部控制建立上限，否则不执行真实请求。实验 B 对所有人都是 faux 回归，不需要 Provider 凭据。

实验 A：运行最短无工具请求。下方 CLI 会调用已配置的真实 Provider，只做受控人工观察。先在 Provider 侧设置硬额度，选择已经核价的低成本模型，把变量值替换成真实 `provider/model:off`。CLI 没有统一的 turn/cost 硬上限，不能只靠 prompt 控制费用。

```bash
PI_LEARNING_MODEL="provider/model:off"
./pi-test.sh --offline --no-session --no-extensions --no-skills \
  --no-prompt-templates --no-context-files --no-tools \
  --model "$PI_LEARNING_MODEL" --mode json "只回复 ok"
```

实验 B：观察一条确定性的工具调用事件流。该用例只使用 faux Provider 和内存中的 `calculate` 工具，不读取业务文件，也不连接真实 Provider。先恢复仓库依赖，再在无网络 namespace 中运行；阅读测试中的 `Agent.subscribe()` 和断言，在 `Agent.processEvents()` 使用调试器 logpoint 记录完整事件，不必修改测试文件。

```bash
cd "$(git rev-parse --show-toplevel)/packages/agent"
env -i HOME=/nonexistent PATH="$PATH" PI_OFFLINE=1 \
  unshare --user --map-root-user --net -- \
  node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run \
  test/e2e.test.ts -t "executes tools and tracks pending tool calls"
```

`env -i` 清除继承环境，固定不可用的 `HOME`，只把当前 `PATH` 和离线标志交给测试进程。若非特权 `unshare` 不可用，改用 `--network none` 容器或公司等价的 egress-deny 环境；在真正隔离前只能阅读该测试，不能把运行结果记为“网络隔离回归”。`--offline` 只关闭启动期更新、目录刷新等网络操作，不会也不应该阻断实验 A 的目标 Provider 请求；`--no-extensions` 防止本地或用户扩展 hook 注入工具，`--no-session` 避免把观察内容持久化到普通 session。

这里不能把 CLI 的 tool allowlist 当作文件系统 sandbox：`read` 接受绝对路径和 `~`，临时 cwd 与 prompt 中的“只读取当前目录”都阻止不了模型读取 cwd 外文件。只有阶段 3B 已做到“仅挂载获准样本 workspace、独立低权限身份、工具执行环境读不到模型凭据或 `/proc/self/environ`”，并通过 cwd 逃逸、认证文件和环境变量的负向读取测试后，才允许真实 Provider 的文件工具 trace。

分别标注两条 trace 的所属层级。若执行了实验 A，CLI trace 包含 session 创建、`agent_start`、`turn_start`、消息流、`turn_end`、`agent_end` 和 session 层的 `agent_settled`；作为回退的 `pi-agent-core` faux 无工具 trace 和实验 B 的工具 trace 都只到 `agent_end`，还没有 session 或 `agent_settled`。工具 trace 还应标出 assistant tool call、`tool_execution_start/end`、`ToolResultMessage` 和下一次模型调用。真实 Provider 只用于无工具人工观察，不纳入自动回归。

### 自动测试的硬隔离

仅约定“使用 faux provider”还不足以证明不会误调真实模型。学习实验和后续 CI 同时采用以下保护：

1. 测试创建独立 `Models` registry，只注册 `fauxProvider()`；不加载 all-providers，也不使用带全局状态的 compat registry。
2. 测试进程不注入任何 Provider 凭据，CredentialStore 使用测试专用空目录或显式空实现。
3. 在无 egress 的容器、network namespace 或 CI job 中运行自动测试；任何 outbound socket 尝试都使 job 失败。
4. 每个测试断言实际选中的 model/provider ID 是 faux。
5. 真实 Provider smoke/eval 使用独立、人工触发的 job、独立凭据和硬成本上限，不与自动回归共享入口。

其中 faux 只替代模型传输与输出轨迹；业务输入仍使用真实或脱敏真实案例。

- 生产版 Pydantic 模型显式使用 `extra="forbid"` 和 strict mode；这是有意收紧，不是照抄 pi 的默认 object Schema 行为。
- `UserMessage | AssistantMessage | ToolResultMessage` 的穷尽分支。
- 多 content block 的增量归约。
- 流内错误与建立请求失败两种错误路径。
- 最终结果只结算一次。

### 可验收产物

- Provider-neutral 消息图和事件状态图。
- TypeScript 到 Python 的类型映射表。

### 通过标准

能在不看 OpenAI 或 Anthropic SDK 细节的情况下，说明一个新 Provider 必须实现哪些契约；pi/TypeScript 的同一 consumer 可消费两个 adapter，Python 的 `ScriptedProvider` consumer 不依赖 Provider 专有事件；参数经过 clone、optional-null 归一和类型转换后仍不合法时，在工具执行前被拒绝。

### 常见误区

- 新代码复制内部兼容 API，而不使用当前 `createModels()` 与 Provider factory。

### 必答问题

1. 为什么 steering 在当前 turn 的工具批完成后、下一次模型调用前注入？
2. follow-up 为什么要等 Agent 本来准备结束时才进入外层下一轮？
3. 工具默认并行时，完成事件顺序与写入模型上下文的结果顺序为何不同？

7. `Agent.subscribe()` 的异步 listener 为什么会影响 core run 何时 settled？它与同步 `void` 的 `AgentSession.subscribe()` 有何不同？

### Python 最小 Agent 的边界

必须立即跑通完整垂直切片，而不是先搭很多抽象：

```text
严格输入模型
→ Provider async event stream
→ assistant message 归约
→ tool call Schema 校验
→ 工具执行与 ToolResultMessage
→ 下一次 Provider 请求
→ 最终消息、事件和统计
```

建议组件只有：

- `Provider` protocol。
- `Tool` protocol 与严格参数模型。
- `AgentState`。
- 一个 loop controller。
- 一个事件 sink。
- 显式 budgets 和 cancellation。

不要在只有一个实现时先设计插件框架、工作流 DSL、分布式队列或通用记忆层。

工程布局、依赖锁定、`pyright` strict、`ruff`、`pytest`、确定性 faux provider、结构化并发和任务泄漏断言统一按[Python 复刻实验工程](./Python复刻实验工程.md)执行；不能用“单个 demo 能运行”代替 LOOP-01–LOOP-13 的自动验收。

### 可验收产物

- Agent loop 状态图和事件时序图。
- 能运行的 Python 最小 Agent。
- LOOP-01–LOOP-13 的网络隔离回归测试。
- 一页“不变量”清单，例如 tool call/result 配对和终态只出现一次。

### 通过标准

能从任意一个中间事件推断合法前驱与后继；能解释每个失败场景如何结束；Python 实现通过全部矩阵，且没有 `Any`、吞异常或隐式无限循环。

### 阶段出口：冻结运行时所有权 ADR

阶段 2 的 Python loop 是理解性复刻，阶段 3A 的 RPC 客户端是集成路线。进入后续结业项目之前必须提交 ADR，明确只选择一条生产主路径：

| 路线 | Agent loop 所有者 | 适用条件 | 后续实现重点 |
| --- | --- | --- | --- |
| A（本计划默认） | pi Node worker；Python 是 API/control plane 与 RPC client | 希望复用 pi 的 Provider、loop、session、扩展和升级能力，可以运维 Node worker | 进程隔离、RPC 版本、session 生命周期、worker drain、Node/Python trace 贯通 |
| B | Python-native runtime；pi 只作为可执行行为参照 | 组织明确要求单一 Python runtime，并接受自行维护 Provider/loop/session/durability 语义 | Python 合约测试、Provider adapter、持久化与恢复、逐项跟踪 pi 行为差异 |

ADR 至少记录：决策驱动因素、被放弃路线、loop/session/effect 真值所有者、升级策略、故障域和撤销条件。未提交 ADR 时，阶段 6 默认采用路线 A；禁止在一次请求中让两套 loop 轮流拥有同一 transcript 或同一工具副作用。

### 常见误区

- 把模型生成 JSON 当成可信参数。
- 并发工具结束后按完成顺序写回，破坏 Provider 预期的调用顺序。
- 只取消 asyncio task，不设计工具对取消的合作响应。
- 重试整个 loop，导致已有副作用重复执行。

### 路线 A：从 faux fixture 迁移到真实 Node worker

[Python 复刻实验工程](./Python复刻实验工程.md)中的 RPC fixture 只证明 framing、关联、事件和进程结算，不是结业项目的生产 worker。阶段 3B 开始另建版本化入口 `company-pi-worker.ts`，沿用同一 `createAgentSessionRuntime()` 组装边界，但按以下三个 profile 逐级开放；不能直接把测试 fixture 改名上线：

| Profile | 模型与工具 | 目的 | 出口证据 |
| --- | --- | --- | --- |
| A0 协议 | 唯一 faux model，`noTools: "all"`；stdin 只接受受信测试脚本 | 验证 Python RPC client 与 worker 生命周期；不是安全或生产 profile | P3 全矩阵、网络隔离、无凭据、无 pending/孤儿进程；已记录直接 RPC `bash` 仍存在 |

`company-pi-worker.ts` 至少固定以下所有权和配置：

1. `ModelRuntime` 只从批准的公司 secret injector/模型网关取得短期凭据；模型 ID 由版本化配置指定，缺失或不匹配时启动失败，凭据不进入 argv、prompt、session 或日志。
2. 默认不做项目资源发现。A1 使用固定 `ResourceLoader`，只返回代码内置并随 artifact 审计的 bash-deny 扩展，不扫描项目或用户目录；Agent 工具只通过 `customTools` 注册阶段 3B 的严格只读工具，并由隔离 runner 执行，不直接启用内置 `read`。runner 只获得当前调用所需的参数、授权 workspace 挂载和工具专用短期凭据，不继承模型凭据或 worker 环境。skills、prompt templates、context files 和其他扩展保持空，直到分别通过 allowlist 评审。
3. Python control plane 独占子进程 stdin/stdout，外部 API 只映射版本化 Pydantic command allowlist，但客户端校验不构成安全边界。当前 `runRpcMode()` 没有服务端 command allowlist，会直接处理完整 `RpcCommand`；A1/A2 因此不能把 stdin 原样交给它。优先为 RPC 入口增加在命令分派前执行、默认拒绝的 `authorizeCommand` 边界；若不修改 pi，则由 `company-pi-worker.ts` 实现等价的严格 dispatcher。每个 profile 只放行完成该用例所需的 `prompt`、`abort` 和只读状态/结果查询；`bash`、`export_html`、任意路径的 `switch_session`、`fork`、`clone`、`set_session_name`、`compact`、模型切换及未来新增 command 默认拒绝。确需 session 管理时只接受服务端解析的 opaque ID，并将写入限制到专用 session 存储，不能接受调用方路径。A1/A2 还必须由上述代码内置扩展安装 `user_bash` handler 作为纵深防御，返回 `exitCode=126` 的替代 `BashResult` 并写审计事件；handler 必须返回结果而不是抛异常，因为 handler 失败后当前实现会继续落到真实 bash。OS sandbox 最后阻止绕过后的未授权进程创建、业务工作区写入和非白名单网络。
4. 每个 worker 绑定已授权的 tenant/workspace/cwd。A0/A1 使用内存 session；进入 L1 前按 ADR 接入获批的 session/operation 存储，定义重启、保留和租户隔离，不能继续把临时目录当生产持久化。
5. worker artifact 固定 pi/Node/配置版本，启动时输出不含秘密的版本与 capability 摘要；Python 握手校验 model、`getActiveToolNames()`、system prompt、session profile 和协议版本，不接受隐式 fallback。`noTools: "builtin"` 只禁用默认激活的内置工具，不保证从 `getAllTools()` 删除其定义；因此测试必须断言实际 active tools 和发给模型的 system prompt，同时把全部已注册定义作为独立 inventory 记录，不能把 inventory 当成激活 allowlist。

迁移门按 A0 → A1 → A2 单向推进。A2 通过仍不等于 L1：还必须关闭[生产化能力清单](./生产化能力清单.md)中 L1 的全部 `Applicable` 阻断项。A1/A2 的负向测试必须遍历当前 `RpcCommand` 的每个未授权成员，并断言拒绝发生在任何 session、文件、进程或 Provider 操作之前；新增 command 在 policy 未显式升级时也必须保持拒绝。任何测试发现未授权 command 可执行、默认内置写工具重新出现、资源发现超出 allowlist 或 egress 超界，立即停止该 worker；此后只能继续不接调用方流量的 A0 协议测试，不能把仍暴露完整 RPC command 面的 A0 当作安全回退环境。

### 可验收产物与通过标准

### 核心模型

```text
SessionManager append-only entry tree（当前内存中或文件中已追加且可解析的会话历史）
  → buildSessionContext()（活动分支 + 最新压缩投影）
  → Agent.state.messages（run 边界上的 Agent transcript）
  → createContextSnapshot()（本次 run 的局部可变 context）
  → transformContext()（可选的 AgentMessage[] 投影）
  → convertToLlm() + build Context（统一的 pi-ai Context）
  → Provider adapter 构造原生 API payload
  → 可选 before_provider_request/onPayload 检查或整体替换
  → 发送替换后的实际请求体
```

### 动手实验

1. 用 Python 解析一份真实 session JSONL，重建 parent/child 树和 active path；对 malformed 行记录诊断并明确跳过或拒绝策略，不能把它算入可恢复 transcript。
2. 创建两个 branch 和一个 fork，验证切换 leaf 不删除原始历史。
3. 触发一次 compaction，验证 `summary + kept tail` 的投影方式。
4. 触发第二次 compaction，分别验证常规路径会传入旧 summary，以及 split-turn 且 `messagesToSummarize` 为空时当前不会合入旧 summary 的边界。
5. 验证切点不会破坏 toolCall/toolResult 配对。
6. 为压缩前后定义事实保真检查：约束、决策、文件修改、失败原因、待办状态分别计算保留率。
7. 在 provider 或工具执行中间终止进程，记录普通 session resume 无法判断外部副作用结果的边界。

- 把 session 文件等同于发送给模型的 messages。
- 认为 branch 会删除另一条历史。
- 只比较 token，不检查事实和约束是否丢失。
- 将 v3 `packages/coding-agent/docs/session-format.md` 与 AgentHarness 的 storage format 4 规范混读。

## 阶段 4：错误、并发、评测与可观测

时间：第 8–9 周。

### 学习目标

- 把失败分到正确层：Provider 建连、stream 中断、完整 turn、context overflow、工具副作用、客户端断连。
- 建立可重复评测，而不是凭一次回答判断 Agent 质量。
- 用 trace、usage、cost 和业务指标解释运行结果。

### 阅读入口

- `packages/ai/src/utils/provider-retry.ts`
- 各 Provider adapter 的 retry 与 error 映射
- `packages/coding-agent/src/core/agent-session.ts` 的 retry、abort 和 compact-and-retry
- `packages/coding-agent/src/core/http-dispatcher.ts`
- `packages/telemetry/README.md`
- `packages/evals/README.md`
- `packages/coding-agent/docs/json.md` 与 `packages/coding-agent/docs/rpc.md`

### 故障注入矩阵

至少覆盖：

- Provider 建连前 transient error 后成功。
- stream 已产生部分内容后断开。
- provider idle timeout、工具 timeout、Agent 总 deadline。
- streaming、tool executing、retry sleep 三处 abort。
- context overflow 触发一次 compact-and-retry。
- 工具副作用已经发生，但结果回传前进程终止。
- 重复 RPC request、客户端断连、worker SIGKILL。

每项记录：可否安全重试、幂等键放在哪里、落盘证据、最终事件、人工或自动 reconciliation。

### 评测实践

从公司目标场景抽取真实或脱敏真实案例，建立版本化数据集。课程阶段先做一个覆盖核心路径、主要失败类型和已知安全威胁的小规模分层集合；具体数量由当前可用案例和预算记录在实验方案中，不能靠复制同类样本凑数。生产发布前再按目标置信区间、检验功效和风险容忍度扩充，执行[生产化能力清单](./生产化能力清单.md)中的量化门禁。每个案例包含：

- 输入与允许读取的上下文。
- 必须满足的事实、约束和工具行为。
- 禁止行为和安全规则。
- 可自动判断部分与必须人工复核部分。
- 失败分类，而不仅是一个总分。

对 baseline/candidate 重复运行，比较任务成功率、事实正确率、安全违规率、p50/p95/p99 延迟、token、估算成本、工具错误和重试。课程小样本只报告原始计数、配对差异和置信区间，不对稀有安全事件作“已经安全”的推断。Provider 账单才是最终成本真值，模型表中的价格只能用于估算。

### 可验收产物

- 分层失败分类和重试/幂等决策表。
- 故障注入报告。
- 真实脱敏评测集 v1、baseline 和 candidate 报告。
- trace 字段与敏感数据策略。

### 通过标准

任何失败都能回答“发生在哪一层、是否已产生副作用、是否可自动重试、用户看到什么终态、怎样审计”；任何模型或 prompt 变更必须经过相同数据集和门禁。

### 常见误区

- 将 429、stream drop、context overflow 和工具异常统一成盲目重试。
- 用同一真实 Provider 测试作为唯一回归来源。
- 将 prompt、tool args、tool results、headers 和凭据默认全部写入日志。
- 只测平均延迟与平均成本，忽略尾延迟和异常切片。

## 阶段 5：耐久性概念与 AgentHarness（storage format 4）

时间：第 10 周。

耐久性概念和运行时选型 ADR 是必修；AgentHarness 源码与崩溃恢复实验是条件选修。准备开放 L3 写副作用、评估采用 Harness 或专门负责耐久运行时的学习者，必须完成选修部分。只交付 L1 只读原型时可把选修安排在结业后。

### 学习目标

- 理解 transcript resume 与 durable operation recovery 的本质区别。
- 理解 intent、uncertain effect、settlement、replay policy 和 durable abort。
- 能评估 Harness 的当前实现范围，而不把 WIP 规范当成现成功能。

### 阅读顺序

必修：

1. `packages/agent/docs/tool-durability.md`
2. `packages/agent/docs/assistant-durability.md`
3. `packages/agent/docs/harness.md` 的 Part 0、3、4、9，以及实现状态表
4. 阶段 2 的运行时所有权 ADR 和[生产化能力清单](./生产化能力清单.md)的副作用章节

条件选修：

1. `packages/agent/docs/telemetry.md`
2. `packages/agent/docs/telemetry-schema.md`
3. `packages/agent/src/harness/` 中与 accept、drive、tool settlement、storage backend 直接对应的实现
4. `packages/coding-agent/src/experimental/` 的 session worker，仅用于了解接入位置

### 必答问题

1. 为什么 accept 只持久化 operation，而不立即执行副作用？
2. `effect_pending` 时进程死亡，`replay="safe"` 与 `replay="never"` 应如何不同？
3. 为什么 durable abort 不能等同于一次调用上下文中的 cancellation？
4. exactly-once 为什么无法仅靠本地状态机保证？
5. lane、operation、immutable entries、mutable values/lists 和 usage ledger 分别解决什么问题？

### 必修设计练习

为“外部副作用已发生、settlement 尚未写入时进程死亡”画状态图，分别给只读、业务幂等写、非幂等写定义 retry/reconcile/manual-review 决策。将它写入运行时所有权 ADR；即使选择稳定 v3 或自研 Python runtime，也不能跳过 unknown outcome。

### Harness 条件选修实验

在 memory、JSONL 或 SQLite backend 上，对以下原子边界逐一 close/reopen/drive：

```text
operation accepted
→ provider intent persisted
→ provider effect pending
→ assistant settlement
→ tool intent persisted
→ tool effect pending
→ tool settlement
→ next turn / operation settled
```

对 safe 与 never replay 工具分别注入崩溃，记录恢复行为和 unknown-outcome 处理。外部系统仍需业务幂等键或 reconciliation；Harness 不会神奇地提供 exactly-once。

### 条件选修验证命令

```bash
cd "$(git rev-parse --show-toplevel)/packages/agent"
node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run \
  --config vitest.harness.config.ts \
  test/harness/memory-conformance.test.ts \
  test/harness/jsonl-session-repo-conformance.test.ts \
  test/harness/runtime/drive-retry-deferred.test.ts
```

### 当前边界

AgentHarness 已实现主要 durable operation 状态机，但 JSONL storage format 4 仍为 WIP。当前主要未完成项或 contract debt 包括 J1 JSONL snapshot compaction、R12 `watchSession()`、T1 telemetry、S3 search、WP08 剩余部分、C1 raw `RemoteSession` 决策和 H1 contract/test closure。R11 schema migration 仅在 format 4 稳定后的首次不兼容变更前激活，当前没有需要执行的 format-4 migration。

Work scheduling、Provider stream resume、multiple writable owners、replication 和 external-effect exactly-once 是 Harness 的明确非目标，不应列成未来自动补齐的缺口。跨进程 lease/fencing、多 owner 协调与 HA 属于宿主平台职责；合规擦除依赖尚未实现的 administrative precise rewrite。

经典 `AgentSession` 与 `AgentHarness` 是两条独立运行线，但 Harness JSONL backend 已支持 legacy coding-agent v3 compatibility：只读 open 在内存中归一且不修改源文件，首次非空 format-4 commit 原子升级源文件。这不同于 R11 schema migration。由于 format 4 仍为 WIP，生产采用前仍需 ADR、备份与回滚验证，不应手工改写 session 文件。

### 可验收产物与通过标准

- 必修：运行时所有权 ADR 增补 durability 决策；提交崩溃点、状态转移、幂等和 reconciliation 图。
- 必修：能解释 transcript resume、operation recovery 与 effect correctness 的差别。
- 选修：完成 classic loop 与 Harness 的 ADR 式对照和 Harness 崩溃恢复实验。
- 选修：能用源码和测试证明 `AgentTool.replay` 在经典 loop 中不生效，只属于 Harness 恢复路径。

## 阶段 6：生产结业项目

时间：第 11–12 周。课程交付等级固定为 L1 内部只读；真正生产化必须继续迭代。

### 推荐题目：真实仓库诊断 Agent

选择当前真实仓库作为第一条垂直切片：

- 输入：真实仓库、真实 Git 历史、真实测试或静态检查输出。
- 第一阶段工具：只读文件、搜索、Git 查询、限定测试、诊断报告。
- 第一阶段禁止写操作，不提供任意网络和任意 shell。
- 第二阶段才增加策略约束的修改工具，并在执行前要求人工审批。
- 自动回归使用 faux provider 控制 Agent 轨迹，业务语料使用真实或脱敏真实数据。
- 课程内真实 Provider 只用于受控 smoke test 和非生产流量评测；只有通过对应生产门禁并获得真实流量授权后，才进入真正的 shadow/canary。

默认按阶段 2 ADR 的路线 A 实现：Python control plane 通过 RPC 管理隔离的 pi Node worker，由 pi 唯一拥有 Agent loop。若 ADR 选择路线 B，则 Python runtime 唯一拥有 loop，pi 只用于对照测试；必须替换下文中对应的 session/operation 设计并记录行为差异，不能同时维护两个真值。

### 必须贯通的链路

```text
严格请求 Schema
→ tenant/workspace/session 授权
→ Agent loop 与 budgets
→ 只读工具 policy + sandbox
→ session/operation 持久化
→ 结构化结果与审计
→ trace/metrics/cost
→ 非生产流量 eval
→ 人工复核
→ 可重复的 shadow/canary 演练
→ kill switch 与回滚 runbook
```

### 交付物

1. 问题定义、非目标和威胁模型。
2. 架构图与关键 ADR。
3. 严格输入/输出 Schema 和工具目录。
4. 真实脱敏评测集、baseline/candidate 结果与失败切片。
5. 幂等、超时、取消、重试、未知结果和恢复策略。
6. trace、metrics、日志去敏、成本预算和告警。
7. 部署设计、健康检查、graceful drain、备份恢复和 RTO/RPO 演练方案。
8. shadow/canary 演练、人工审批、回滚和 kill switch runbook；真实流量证据列入后续里程碑。

### 毕业答辩问题

- 为什么这个场景需要 Agent，而不是确定性工作流或普通检索服务？
- 哪些决定交给模型，哪些必须由代码和 policy 强制？
- 如果工具已经修改外部系统但进程死了，怎样发现、去重和补偿？
- 如果模型质量提升 3%，但 p95 延迟和成本翻倍，是否上线？门槛是什么？
- 哪些数据绝不能进入 Provider、session、trace 或 eval artifact？
- 怎样在 10 分钟内停止所有新副作用，同时保留审计与可恢复状态？

### 最终通过标准

课程毕业门槛必须有证据，不接受“理论上支持”：

- 一个真实窄场景端到端可用，不是只有 UI 或接口的空壳。
- 达到[生产化能力清单](./生产化能力清单.md)中 L1 内部只读适用的门禁；写副作用项目不得以本课程范围为上线依据。
- 故障注入覆盖 provider stream、只读 tool、settlement、重复请求和 worker 退出；写副作用 effect 场景可以通过隔离实验验证，不连接真实业务写权限。
- 小规模课程评测达到预先冻结的质量、延迟、成本和安全阈值，并明确其统计局限。
- 完成 shadow/canary、审批、熔断与回滚演练；若没有授权的真实流量环境，必须明确标注为演练而非生产验证。
- 生产差距清单为扩大评测、真实 shadow/canary、L2–L4 副作用、HA 和灾备列出负责人、依赖、证据要求与阻断条件。

## 计划外选修

### Multi-agent

完成单 Agent 后再读 `packages/coding-agent/examples/extensions/subagent/`。依次实验单子 Agent、有界 fan-out/fan-in 和顺序 chain。生产实现必须补充工具白名单、独立上下文、wall-clock/token/cost 预算、取消传播、输出上限、部分失败聚合和 durable recovery。仓库示例是编排原型，不是生产框架。

### TUI

只有公司产品需要终端界面时再读 `packages/tui/README.md`、`packages/coding-agent/docs/tui.md`、virtual terminal 测试和 interactive mode。验收需覆盖 ANSI、CJK、emoji、resize 和 IME，不能只靠肉眼。

### MCP

在工具契约、认证和隔离已经掌握后，再把 MCP 作为一种标准化 client-host-server 工具边界研究。先读官方 architecture，再读 security best practices；不要把“使用 MCP”误认为已经解决了工具授权和远端服务安全。
